# 分布式：一个心智，多具身体（设计说明）

> 状态：**已在 1.0.0 实现**（含 B4「灵魂桥作为只读成员入网」，见 §7）。本文记录 2026-10-05 与所有者逐条拍板的决定、组网方案的实测结论与实施计划；实现完成后，相关内容并入 [ARCHITECTURE.md](ARCHITECTURE.md)、[API.md](API.md)、[SOUL_SYNC.md](SOUL_SYNC.md) 与 [灵魂仓库规范](SOUL_REPO_SPEC.md)（升 v8），本文转为设计说明。目标版本 **1.0.0**，一次做完（不分 0.7 / 0.8 / 0.9 发布）。

## 0. 现状与问题

- 灵魂仓库（git）是唯一跨身体共享的东西。提交与推送只在一轮结束时发生（醒来 / 做梦 / 对话结束、身份修改）；一轮中途写的记忆、用 `shell` 直接改的灵魂目录，要等这一轮结束才进仓库。推送失败只记在 `status.lastError`，她不知道。
- 冲突全部由基座静默裁决：常驻记忆条目级合并、`agent.json` 字段合并，其余文件取较新的一方。
- 会话、消息、时间线、心脏、审批、预算都在每具身体自己的 SQLite 里：每具身体是一个独立的她，彼此只通过 git 共享记忆。
- 飞书长连接是集群模式：同一个应用有多条长连接时，每条事件只投递给其中一个客户端。多具身体都配同一个机器人，消息会随机落到其中一具。

## 1. 触碰即同步（灵魂仓库）——已实现

| 决定 | 内容 |
|---|---|
| 怎么判断「碰了」 | **每次工具调用结束后**（含 `shell`、自造工具、子 agent 的工具、跨身体执行的工具）在串行队列里跑一次 `git status --porcelain`；不做文件监听 |
| 提交 | 有变更就立即提交，一次工具调用一个提交。提交信息按变更的路径写清楚做了什么（`记忆：新增一条（<body>）`、`笔记：<路径>（<body>）`、`人格：改写（<body>）`），保持「git 历史就是自传」 |
| 推送 | 3 秒去抖合并推送；一轮结束时强制推送一次。推送成功后经网状层广播新提交，其他身体立即 fetch（仍然没有定时同步） |
| 归属 | 每个提交记下是哪个会话、哪一轮、哪次工具调用造成的，推送失败时据此找到要提醒的会话 |

**推送失败**：按原因分为网络 / 超时、认证（部署密钥）、身份守卫、重试后仍被拒。

- 网络类先**静默**按指数退避多次重试（暂定 5 次，约 2 分钟内），仍失败才提醒；其他类型立即提醒。
- 提醒走插话：碰记忆的那一轮还在进行，就往它的 inbox 送一条环境输入（通道「灵魂同步」），说明失败原因和建议。那一轮已经结束，就在原会话里以同样的环境输入**开启新的一轮**（控制台可见），由她决定怎么处理。醒来或做梦造成的变更没有会话，提醒进入「主动消息」会话。

**冲突改为混合裁决**：

| 文件 | 规则 |
|---|---|
| `memories/*.md` | 不变：条目级三方合并，自动完成 |
| `agent.json` | 不变：字段级合并，自动完成 |
| `journal/<身体>/`、`bodies/<身体>.json` | 不变：天然无冲突 |
| `SOUL.md`、`notes/**`、`skills/**`、顶层其他文本 | 双方都改过时，先按「较新的一方」自动合并（仓库不能卡住），然后把落选的一方存进 `.incoming` 副本（规范 §3.3 已忽略 `*.incoming*.md`，不入库），并以插话交给造成本地变更的那个会话：她看两个版本，决定保留哪一版或手动合并；不处理也不影响同步 |

## 2. 统一心智：已拍板的决定

| 编号 | 问题 | 决定 |

| B3 | 端点信息 | 账户服务：用户注册账户，一个账户下绑定多个 agent；后改为部署在所有者服务器上的同步服务（§4），并且不存端点（ICE 实时交换） |
| B4 | 桥接身体（Hermes / OpenClaw） | 作为**只读成员**入网：能看到在场状态与会话，不被调度 |

| C2 | 断网分区 | 每个分区各自活（各有协调者），重新连上后合并 |
| C3 | 在哪里运行 | 基座给每具身体打分并推荐，她可以接受或改掉；可以同时选多具身体（同一个她的多条意识流） |
| C4 | 跨身体工具 | 1.0 就要：在 A 上思考，可以调用 B 的工具 |

| C6 | 新对话由谁接 | 用户联系的是哪具身体就由哪具接；**她可以随时决定改到任意一具身体上回复或操作** |
| C7 | 飞书 | 由部署者指定一具固定的身体持有长连接 |
| C8 | 全网统一的配置 | 模型供应商与 Key、权限、预算（全网合计）、性格参数、听觉与语音配置全网统一；只有适配器与保密库按身体。每个分区带修订号（修改时刻），较新的生效；有同步功能之前配好、修订号还是 0 的分区，启动时按数据文件的修改时刻补上（`backfillRevs`），空的与缺省的不补 |
| C9 | 急停与暂停 | 全网生效；另提供「只停这具身体」 |
| C10 | 多只耳朵与发声 | 跨身体去重；由听到这句话的耳朵所在的身体发声，其次是用户最近交互的身体 |
| D1 | 发布 | 一次做到 1.0.0 |

### 2.1 什么属于心智，什么属于身体

| 归属 | 内容 |
|---|---|
| 心智（网上复制） | 心脏状态、会话与消息、进行中轮次的快照、未完成的念头、想分享的一句话、审批、急停与暂停、时间线、子 agent、全网配置（C8）、预算用量 |
| 心智（持久） | 灵魂仓库（git），同时是成员信任的根 |
| 身体（只在本地） | 适配器、传感器、设备工具、耳朵与扬声器、保密库 `vault/`、自造工具的实现、网关令牌、部署私钥、网状层私钥 |

### 2.2 协调者与分区

- 2 到 5 台经常断网的设备，用多数派共识不合适：两台设备一断开就谁都选不出来。所以采用 **AP 模型**。每个连通分量里，按确定的打分选出协调者：外接电源、在线时长、部署者设定的优先级、节点 id 作平局裁决。协调者持有心脏，负责醒来抽样与放置推荐。
- 复制的数据带混合逻辑时钟（HLC）。消息与时间线只追加，全局 id 为「身体 + 序号」，合流时直接取并集。心脏状态按字段规则合并：睡眠压力 S 取较大值，驱动力取合流后新协调者的，未完成念头取并集。审批以第一个决定为准。
- 做梦的整理租约改由网状层的锁提供（毫秒级）；分区中仍然走 git 租约兜底。

### 2.3 醒来与放置

- 醒来时的内省额外看到一份**身体概况**：每具身体的电量、温度、是否充电、负载、联网、可用模型与剩余预算、独有的工具（相机、桌面、GPU）、用户是否在旁边，以及基座的推荐。她的回答在 `{engage, intent}` 之外多一个 `where`（一具或多具身体）。
- 同时运行在多具身体上时，是**同一个她**的多条意识流：都用她的人格与记忆，在系统提示的「其他会话」里互相看到对方的实时进展（现有机制扩展到跨身体）。

### 2.4 跨身体工具与「到别处去」

- 工具表里，其他身体的工具以 `<身体>.<工具>` 挂载（设备工具、`shell`、自造工具），经网状层 RPC 执行。闸门与审批由**工具所在的身体**按全网统一的权限判断，审计在两边都记。
- 新增工具 `move_to(body)`：把当前这一轮（对话或醒来）转到另一具身体继续，上下文与进展快照随之迁移；对话中的回复从新身体所在的通道发出（如果那个通道就在那具身体上）。

### 2.5 在场状态与对话

- 广播 `presence`：`{conv, body, turn, status, channel}`。任何一端的控制台都能看到「她正在 某身体 上、经 某通道 和你说话」。
- 同一会话同时只有一个持有身体在执行。其他身体收到发给这个会话的消息时，转发给持有者作为插话或打断，复用现有的 inbox。
- 会话与消息全网复制，`activity` 事件跨网转发：在 A 上进行的一轮，可以在 B 的控制台里实时看到。
- 主动消息只发一次：飞书由持有长连接的身体发送；系统通知只在用户可能在场的身体上弹出。

### 2.6 耳朵

- 多只耳朵听到同一句话时，按开始时刻是否重叠（1.5 秒内）和文本相似度跨身体去重，保留最长或置信度最高的那一条。
- 她用 `voice_speak` 时，由听到这句话的耳朵所在的身体发声；没有对应的耳朵时，由用户最近交互的身体发声。

## 3. 组网：WebRTC + 自己服务器上的同步服务（不内嵌 ZeroTier / Tailscale）

所有者的要求：服务器只帮助建立连接，自动找最短路径；两边都打不通时由服务器直接中转；安全第一，能用成熟方案就不自己造。

### 3.1 候选方案

| 方案 | 能否在 Termux 上运行 | 许可证 | 结论 |
|---|---|---|---|
| Tailscale（`tailscaled --tun=userspace-networking`）+ 自建 Headscale | 只有社区补丁版，每具身体多一个 30–50 MB 的 Go 程序，经 SOCKS5 访问 | BSD-3 | 账户体系与 Headscale 是两套；多一个守护进程 |
| ZeroTier（自定义 planet / moon） | `zerotier-one` 要 TUN（安卓无 root 拿不到）；libzt 的 Node 绑定要原生编译且没有合并 | 客户端 MPL-2.0，**控制器在 `nonfree/` 下是源码可见许可** | 安卓上跑不起来，控制器不能放进 AGPL 的服务 |
| App 的 VpnService | 能 | — | 安卓同一时间只能有一个 VPN，会和用户自己的 VPN 冲突 |
| 自研 UDP 打洞 + 自研加密与可靠传输 | 能（实测见 §3.2） | AGPL | 加密握手、可靠传输都是安全敏感的轮子，不自己造 |
| **WebRTC（ICE + DTLS + SCTP）+ coturn** | `node-datachannel`（libdatachannel 的绑定，底层 OpenSSL / libjuice / usrsctp）有 android-arm64 预编译包，实测能用 | MPL-2.0（兼容 AGPL）；coturn 为 BSD | **采用**：穿透、加密、可靠传输都是久经考验的标准实现；中转用标准 TURN |

### 3.2 实测（2026-10-05）

测试环境：一台家用宽带后的 Linux 主机，一部走**蜂窝网络**的安卓手机（Termux，Node v24.18.0，Android 9，arm64）。测试点的公网地址不在这里记录。

| 测试 | 结果 |
|---|---|
| IPv4 映射（同一本地端口向多台 STUN 服务器发送） | 主机：端点无关映射（EIM）。手机：**对称 NAT**（运营商级 NAT），每个目的地址的映射端口都不同 |
| IPv6 | 手机有公网 IPv6、端口保留；入站可达性**还没测**（主机没有 IPv6 出口） |
| 普通 UDP 打洞 | 0 包 |
| 生日悖论打洞（手机 256 个 socket，主机撒随机端口） | 约 1 秒打通，之后双向约 1.5 万包。说明自研也可行，但最终不采用（见 §3.1） |
| `node-datachannel` 在手机上 | 预编译包直接装上；同一进程两端经 ICE + DTLS + SCTP 建立数据通道 196 ms；反复建立 / 关闭 5 次无泄漏，内存 45 MB。**注意**：不要在原生回调里直接 `process.exit()`（会触发 bionic 的 free 检查而崩溃），正常关闭流程没有问题 |
| 同步服务整套（Caddy + 同步服务 + coturn）本机部署 | `start.sh` 一行跑通；HTTPS、健康检查、HTTP→HTTPS 跳转正常 |
| 两具身体经同步服务的 WebSocket 信令建立 WebRTC | 默认策略直连 194 ms；**强制只走 TURN**（relay↔relay）302 ms 打通 |
| coturn 加固 | 中转到私有地址被拒绝（日志 `peer IP denied`）；伪造的 TURN 凭据拿不到中转地址 |

对称 NAT 与端口受限 NAT 之间标准 ICE 打不通（libjuice 不做端口预测），这时走 TURN 中转，符合「打不通由服务器直接中转」。

### 3.3 网状层（`runtime/src/mesh/`）——已实现（连接层），统一心智在其上实现中

- **节点身份**：每具身体一把 ed25519 节点密钥（`secrets/mesh_ed25519`，0600），公钥写入灵魂仓库 `bodies/<body>.json` 的 `meshKey`（规范 v8）。**信任根是灵魂仓库**，同步服务只是目录与信令。
- **建立连接**：经同步服务的 WebSocket 交换 SDP 与 ICE 候选；ICE 依次尝试局域网地址、IPv6、STUN 反射地址，打不通时用 TURN 中转，并在连接期间持续检查，网络变化时 ICE 重启，选最优路径。
- **防中间人**：信令内容（含 DTLS 证书指纹）由发送方节点私钥签名，接收方用**灵魂仓库**里登记的公钥验证，并检查协议版本、agent id（防止跨 agent 重放）、时间戳与随机数防重放（随机数只在内存里，所以签于本次启动一分钟以前的信封一律不收）；数据通道打开后，双方再用节点密钥对 DTLS 指纹（连同 agent id）做一次挑战与应答。所以同步服务或中转服务器即使被攻破，也无法冒充身体或解密内容。网状层协议版本为 2（协议 1 的信封与通道认证不带 agent id），版本不同的身体连不上，同一个 agent 的身体要一起升级。
- **钉住（TOFU）**：每具身体第一次见到另一具时记下它登记的公钥与类型；之后公钥变了、或从灵魂桥变成运行基座，在控制台确认之前不连接。灵魂仓库被人改了登记，也要经过人确认才能顶替一具身体。
- **传输**：SCTP 数据通道（可靠有序）承载 RPC、事件与复制日志；大文件分块。
- 协议细节见 [`sync/docs/PROTOCOL.md`](../sync/docs/PROTOCOL.md)。

## 4. 同步服务（`sync/`，部署在所有者的服务器上，对所有人开放）

与仓库其他部分没有代码依赖的独立模块：在服务器上 clone 仓库后 `cd sync && ./start.sh` 一行跑起来。详见 [`sync/README.md`](../sync/README.md)。

| 部分 | 实现 |
|---|---|
| 账户 | OpenID Connect 登录（openid-client；账号由外部身份服务提供，不保存它发的令牌）；一个账户下多个 agent，**agent 登记按账户隔离**（agent id 不是秘密，全局唯一会被抢占） |
| 绑定身体 | OAuth 2.0 设备授权（RFC 8628 的语义）：身体显示短码与公钥指纹，人在网页上登录、输入、核对、批准；令牌只存哈希 |
| 目录与信令 | WebSocket：在场（谁在线）、同一 agent 的身体之间转发信令、签发 TURN 凭据 |
| STUN / TURN | coturn，`use-auth-secret` 的有时效凭据；禁止中转到私有地址；配额与限流 |
| HTTPS | Caddy 自动证书 |

**与 B3 的决定有一处出入，需要所有者知悉**：原计划「每个 agent 存储所有端点信息」。改用 WebRTC 后，端点在身体在线时经信令实时交换（ICE），离线的身体本来也连不上，所以**同步服务不存任何 IP 或端点**：账户下存的是每个 agent 的身体登记（名字、类型、版本、节点公钥、最近在线时间）。这样更安全，也少保存了个人数据。

## 6.1 信任边界

同一个 agent 的所有身体彼此完全信任：另一具身体可以经 `body_call` 在这里执行命令、写自造工具，模型 Key 也会同步过去。任何一具身体被攻破，等于整个 agent 被攻破——这与「每具身体都持有灵魂仓库的写权限」是同一条边界，不是新增的风险。同步服务与中转服务器不在这条边界之内：它们被攻破只会让身体之间连不上，冒充不了身体、看不到内容，也不能让身体崩溃（发来的每条消息按严格形状检查，因此拉取灵魂仓库最快一分钟一次，提醒截断并限频）。

彼此信任不等于不设防：一具出错或被攻破的身体发来的数据，同样不能弄坏其他身体的进程与数据库。所以由对方触发的回调都接住异常；复制来的对话与时间线逐字段检查（编号段与作者对得上，实时只收对方自己写的）；用量只收对方自己的；全网设置的修改时刻不能在未来、只留认得的键；急停「停优先」（解除只解除对方明确解除的那几次急停）；转来的一轮只取白名单字段、就地处理；别处的审批按「身体/编号」区分。细节见 [ARCHITECTURE.md §6.2](ARCHITECTURE.md)。吊销一具身体：在同步服务上解绑，并在灵魂仓库删掉它的部署公钥与 `bodies/<身体>.json`。
