# 分布式：一个心智，多具身体（1.0 设计稿）

> 状态：**设计稿，尚未实现**。本文记录 2026-10-05 与所有者逐条拍板的决定、组网方案的实测结论与实施计划；实现完成后，相关内容并入 [ARCHITECTURE.md](ARCHITECTURE.md)、[API.md](API.md)、[SOUL_SYNC.md](SOUL_SYNC.md) 与 [灵魂仓库规范](SOUL_REPO_SPEC.md)（升 v8），本文转为设计说明。目标版本 **1.0.0**，一次做完（不分 0.7 / 0.8 / 0.9 发布）。

## 0. 现状与问题

- 灵魂仓库（git）是唯一跨身体共享的东西。提交与推送只在一轮结束时发生（醒来 / 做梦 / 对话结束、身份修改）；一轮中途写的记忆、用 `shell` 直接改的灵魂目录，要等这一轮结束才进仓库。推送失败只记在 `status.lastError`，她不知道。
- 冲突全部由基座静默裁决：常驻记忆条目级合并、`agent.json` 字段合并，其余文件取较新的一方。
- 会话、消息、时间线、心脏、审批、预算都在每具身体自己的 SQLite 里：每具身体是一个独立的她，彼此只通过 git 共享记忆。
- 飞书长连接是集群模式：同一个应用有多条长连接时，每条事件只投递给其中一个客户端。多具身体都配同一个机器人，消息会随机落到其中一具。

## 1. 触碰即同步（灵魂仓库）

| 决定 | 内容 |
|---|---|
| 怎么判断「碰了」 | **每次工具调用结束后**（含 `shell`、自造工具、子 agent 的工具、跨身体执行的工具）在串行队列里跑一次 `git status --porcelain`；不做文件监听 |
| 提交 | 有变更就立即提交，一次工具调用一个提交。提交信息按变更的路径写清楚做了什么（`记忆：新增一条（<body>）`、`笔记：<路径>（<body>）`、`人格：改写（<body>）`），保持「git 历史就是自传」 |
| 推送 | 3 秒去抖合并推送；一轮结束时强制推送一次。推送成功后经网状层广播新提交，其他身体立即 fetch（仍然没有定时同步） |
| 归属 | 每个提交记下是哪个会话、哪一轮、哪次工具调用造成的，推送失败时据此找到要提醒的会话 |

**推送失败**：按原因分为网络 / 超时、认证（部署密钥）、身份守卫、重试后仍被拒。

- 网络类先**静默**按指数退避多次重试（暂定 5 次，约 2 分钟内），仍失败才提醒；其他类型立即提醒。
- 提醒走插话：碰记忆的那一轮还在进行，就往它的 inbox 送一条环境输入（通道「灵魂同步」），说明失败原因和建议。那一轮已经结束，就在原会话里以同样的环境输入**开启新的一轮**（控制台可见），由她决定怎么处理。醒来或做梦造成的变更没有会话，提醒进入「主动消息」会话。

**冲突改为混合裁决**：

| 文件 | 规则 |
|---|---|
| `memories/*.md` | 不变：条目级三方合并，自动完成 |
| `agent.json` | 不变：字段级合并，自动完成 |
| `journal/<身体>/`、`bodies/<身体>.json` | 不变：天然无冲突 |
| `SOUL.md`、`notes/**`、`skills/**`、顶层其他文本 | 双方都改过时，先按「较新的一方」自动合并（仓库不能卡住），然后把落选的一方存进 `.incoming` 副本（规范 §3.3 已忽略 `*.incoming*.md`，不入库），并以插话交给造成本地变更的那个会话：她看两个版本，决定保留哪一版或手动合并；不处理也不影响同步 |

## 2. 统一心智：已拍板的决定

| 编号 | 问题 | 决定 |
|---|---|---|
| B1 | 网络范围 | 必须跨网络：手机走蜂窝、电脑在家、可能还有服务器 |
| B2 | 组网 | 内嵌同类能力，公网服务器只用于建立第一次 P2P 连接（像 ZeroTier 的 moon），之后自动找最短路径；见 §3 |
| B3 | 端点信息 | 官网提供账户服务：用户注册账户，一个账户下绑定多个 agent，每个 agent 记录它全部身体的端点；见 §4 |
| B4 | 桥接身体（Hermes / OpenClaw） | 作为**只读成员**入网：能看到在场状态与会话，不被调度 |
| C1 | 心脏 | 单一的逻辑心脏，由协调者持有，各身体的感觉都汇入 |
| C2 | 断网分区 | 每个分区各自活（各有协调者），重新连上后合并 |
| C3 | 在哪里运行 | 基座给每具身体打分并推荐，她可以接受或改掉；可以同时选多具身体（同一个她的多条意识流） |
| C4 | 跨身体工具 | 1.0 就要：在 A 上思考，可以调用 B 的工具 |
| C5 | 对话记录 | 只在网上复制；新身体入网时从其他身体补齐；不进 git |
| C6 | 新对话由谁接 | 用户联系的是哪具身体就由哪具接；**她可以随时决定改到任意一具身体上回复或操作** |
| C7 | 飞书 | 由部署者指定一具固定的身体持有长连接 |
| C8 | 全网统一的配置 | 模型供应商与 Key、权限、预算（全网合计）、性格参数、听觉与语音配置全网统一；只有适配器与保密库按身体 |
| C9 | 急停与暂停 | 全网生效；另提供「只停这具身体」 |
| C10 | 多只耳朵与发声 | 跨身体去重；由听到这句话的耳朵所在的身体发声，其次是用户最近交互的身体 |
| D1 | 发布 | 一次做到 1.0.0 |

### 2.1 什么属于心智，什么属于身体

| 归属 | 内容 |
|---|---|
| 心智（网上复制） | 心脏状态、会话与消息、进行中轮次的快照、未完成的念头、想分享的一句话、审批、急停与暂停、时间线、子 agent、全网配置（C8）、预算用量 |
| 心智（持久） | 灵魂仓库（git），同时是成员信任的根 |
| 身体（只在本地） | 适配器、传感器、设备工具、耳朵与扬声器、保密库 `vault/`、自造工具的实现、网关令牌、部署私钥、网状层私钥 |

### 2.2 协调者与分区

- 2 到 5 台经常断网的设备，用多数派共识不合适：两台设备一断开就谁都选不出来。所以采用 **AP 模型**。每个连通分量里，按确定的打分选出协调者：外接电源、在线时长、部署者设定的优先级、节点 id 作平局裁决。协调者持有心脏，负责醒来抽样与放置推荐。
- 复制的数据带混合逻辑时钟（HLC）。消息与时间线只追加，全局 id 为「身体 + 序号」，合流时直接取并集。心脏状态按字段规则合并：睡眠压力 S 取较大值，驱动力取合流后新协调者的，未完成念头取并集。审批以第一个决定为准。
- 做梦的整理租约改由网状层的锁提供（毫秒级）；分区中仍然走 git 租约兜底。

### 2.3 醒来与放置

- 醒来时的内省额外看到一份**身体概况**：每具身体的电量、温度、是否充电、负载、联网、可用模型与剩余预算、独有的工具（相机、桌面、GPU）、用户是否在旁边，以及基座的推荐。她的回答在 `{engage, intent}` 之外多一个 `where`（一具或多具身体）。
- 同时运行在多具身体上时，是**同一个她**的多条意识流：都用她的人格与记忆，在系统提示的「其他会话」里互相看到对方的实时进展（现有机制扩展到跨身体）。

### 2.4 跨身体工具与「到别处去」

- 工具表里，其他身体的工具以 `<身体>.<工具>` 挂载（设备工具、`shell`、自造工具），经网状层 RPC 执行。闸门与审批由**工具所在的身体**按全网统一的权限判断，审计在两边都记。
- 新增工具 `move_to(body)`：把当前这一轮（对话或醒来）转到另一具身体继续，上下文与进展快照随之迁移；对话中的回复从新身体所在的通道发出（如果那个通道就在那具身体上）。

### 2.5 在场状态与对话

- 广播 `presence`：`{conv, body, turn, status, channel}`。任何一端的控制台都能看到「她正在 某身体 上、经 某通道 和你说话」。
- 同一会话同时只有一个持有身体在执行。其他身体收到发给这个会话的消息时，转发给持有者作为插话或打断，复用现有的 inbox。
- 会话与消息全网复制，`activity` 事件跨网转发：在 A 上进行的一轮，可以在 B 的控制台里实时看到。
- 主动消息只发一次：飞书由持有长连接的身体发送；系统通知只在用户可能在场的身体上弹出。

### 2.6 耳朵

- 多只耳朵听到同一句话时，按开始时刻是否重叠（1.5 秒内）和文本相似度跨身体去重，保留最长或置信度最高的那一条。
- 她用 `voice_speak` 时，由听到这句话的耳朵所在的身体发声；没有对应的耳朵时，由用户最近交互的身体发声。

## 3. 组网：自己实现，不内嵌 ZeroTier / Tailscale

### 3.1 候选方案

| 方案 | 能否在 Termux 上运行 | 许可证 | 公网节点的角色 | 结论 |
|---|---|---|---|---|
| **Tailscale**（`tailscaled --tun=userspace-networking`）+ 自建 Headscale | 社区补丁版可以在无 root、无 `/dev/net/tun` 的 Termux 上运行，但不是官方构建；只能经 SOCKS5 / 端口转发访问，每具身体多一个约 30–50 MB 的 Go 二进制 | BSD-3，兼容 | DERP 在 P2P 失败时**持续中转流量**，这是它的设计 | 违背「服务器不持续分发流量」；还要维护 Headscale 自己的一套用户体系，和官网账户是两套；多一个守护进程 |
| **ZeroTier**（自定义 planet / moon） | `zerotier-one` 需要 TUN 设备（安卓无 root 拿不到）；用户态的 libzt 只有一个未合并的 Node 绑定分支，需要原生编译（node-gyp），违背「无原生依赖」 | 客户端 1.16 起为 MPL-2.0，**网络控制器在 `nonfree/` 下，是源码可见许可**，不能放进 AGPL 的官网服务 | moon 只帮助建立连接，但打洞失败时仍由根服务器中转 | 安卓上跑不起来；控制器的许可证不合适 |
| 走 App 的 VpnService | 能运行 | — | — | 安卓同一时间只能有一个 VPN，会和用户自己的 VPN 冲突 |
| **自己实现**（Node 内置 `dgram` + `crypto`） | 能，和运行基座同一个进程、同一个 `main.cjs` | 本仓库 AGPL | **只做会合**（交换端点、STUN），默认不中转 | **采用** |

### 3.2 实测（2026-10-05）

测试环境：一台家用宽带后的 Linux 主机，一部走**蜂窝网络**的安卓手机（Termux，Node 24）。测试脚本是零依赖的 Node 程序，测试点公网地址不在这里记录。

| 测试 | 主机（家用宽带） | 手机（蜂窝） |
|---|---|---|
| IPv4 映射：同一本地端口向多台 STUN 服务器发送 | 映射端口相同：**端点无关映射（EIM）** | 映射端口随目的地址变化：**对称 NAT**（运营商级 NAT） |
| IPv6 | 本机没有可用的 IPv6 出口 | 公网 IPv6，端口原样保留（无 NAT）；入站是否被运营商防火墙拦截，**还没测**（需要一个有 IPv6 的对端） |
| 普通 UDP 打洞（双方互发 20 秒） | 0 包 | 0 包 |
| **生日悖论打洞**（手机开 256 个 socket 发往主机端点；主机向手机的公网 IP 撒随机端口） | 1.0 秒命中 | 0.8 秒命中；之后 25 秒双向收发约 1.5 万个包 |

结论：

- EIM 和对称 NAT 之间，用生日悖论打洞约 1 秒就能直连，纯 Node 内置能力就能做到。
- 两侧都是对称 NAT 时（例如两部都走蜂窝的手机），打洞基本不可行。这时依次尝试 IPv6 直连（蜂窝网络普遍有公网 IPv6）、经第三具身体多跳转发、最后才是部署者显式开启的服务器中转（缺省关闭）。
- Cloudflare 公共 STUN（`stun.cloudflare.com:3478`）在两种网络下都有回应，可以作为缺省 STUN；部分国内 STUN 在蜂窝网络下没有回应。

### 3.3 网状层设计（`runtime/src/mesh/`）

- **节点身份**：每具身体一把 ed25519 节点密钥（`secrets/mesh_ed25519`）。公钥写入 `bodies/<body>.json` 的 `meshKey`（规范 v8）。**信任根是灵魂仓库**，官网只是目录：握手时验证对端公钥是否登记在灵魂仓库里，所以即使官网被攻破，也无法把陌生节点塞进网里。
- **握手与加密**：类 Noise-IK，ed25519 签名加 X25519 交换密钥，ChaCha20-Poly1305 加密（Node 内置 crypto 都有），带前向保密与防重放。
- **候选路径**：局域网地址（UDP 广播发现）、公网 IPv6、STUN 得到的 IPv4 映射、生日悖论端口、经其他身体转发、部署者开启的服务器中转。
- **选路**：仿 Tailscale 的 disco 方式。连接建立后，在所有候选路径上周期性发 ping，测 RTT 与丢包，取最优路径；网络变化（切 Wi-Fi、换基站）时立即重新探测，自动升级到更短的路径。多跳时由中间的身体按「距离向量 + RTT」转发。
- **传输**：UDP 上一层轻量的可靠有序消息通道（序号、确认、重传、窗口），承载 RPC、事件与复制日志。大文件（附件、图片）分块传输，可以续传。
- **会合**：每具身体启动时、网络变化时，向会合服务登记自己的候选端点，并订阅同一 agent 的其他身体的端点变化。之后的连接与选路都在身体之间直接完成，会合服务不经手业务流量。

## 4. 官网账户服务（会合与目录）

官网目前只有静态页面，加一个用作下载镜像源的 Worker。新增：

| 部分 | 实现（暂定，见 §6 待定） |
|---|---|
| 账户 | 注册 / 登录；一个账户下多个 agent（以 `agent.json` 的 `id` 标识，显示名可改） |
| 绑定身体 | 设备码流程：身体（控制台或安装器）显示一个短码，用户在官网登录后输入，完成绑定；身体获得一个只能登记本 agent 端点的令牌 |
| 目录 | 每个 agent 的身体列表：节点公钥、候选端点、最近在线时间。端点只保留最近一次登记，过期自动清除 |
| 信令 | WebSocket：身体在线时保持一条连接，端点变化时实时推送，打洞时交换时机 |
| STUN | 缺省用 Cloudflare 公共 STUN；部署者的公网服务器可以运行 `quetzal rendezvous`，同时提供 STUN（两个端口，用来判断 NAT 类型）与信令备份 |

- 官网是公开站点，这个服务面向所有 Quetzal 用户，所以隐私页与条款要随之更新：会保存哪些数据（账户、agent 名单、节点公钥、最近的端点），保存多久，不保存什么（记忆、对话、业务流量都不经过官网）。
- 不想用官网账户的部署者，可以只用局域网发现，或者手动填写对端地址。
