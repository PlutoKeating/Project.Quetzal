# 灵魂仓库规范（Soul Repository Specification）v14

本规范定义用于灵魂同步的 git 仓库：它的目录树、固定内容、文件格式、提交约定与认证方式。它是 agent 自己的**私有**仓库，对内容不设任何检查。凡是读写灵魂仓库的实现（运行基座 `runtime/src/memory/soul-repo.ts`、灵魂桥 `bridge/`，以及将来的其他实现）都**必须**遵守。文中「必须 / 不得 / 应当 / 可以」对应 MUST / MUST NOT / SHOULD / MAY。

实现会强制执行其中可以机器检查的部分：远端地址与私钥检查、固定内容补齐、git 的执行安全（§5.2）。

版本历史：
- **v14**：§3.10 身体登记新增可选的 `uuid`：绑定到设备的身体 uuid（运行基座由设备标识的哈希派生，RFC 9562 version 8；取不到设备标识时为随机的 version 4），工具用它指一具身体。**不得**写入原始的设备标识。其他身体解析 uuid 时以登记为准，再核对对方经网状层自报的一致；同一个 uuid 被登记给多具身体时**必须**拒绝解析，**不得**替用户自动改。§3.1 的示例改为当前版本号。v13 仓库无需迁移即符合 v14：运行基座升级后下一次更新自己的登记时补上 `uuid`。
- **v13**：新增 §3.13「路径在每一种身体上都放得下」：Windows 身体加入后，仓库里的每个路径都**应当**能写到 Windows 的磁盘上——不用 Windows 的保留名（`CON`、`NUL`、`COM1` 等，带不带扩展名都算）、不以点或空格结尾、不含 `< > : " \ | ? *` 与控制字符、不出现只差大小写的两个路径；实现写入时**必须**规避（§3.9 的路径段规则、§3.10 的身体名、§3.12 的技能名相应收紧）。已经存在的放不下的路径，Windows 上的实现**必须**照常克隆、拉取、合并与推送，只是不把它们写进工作区，在仓库里原样保留，并提醒 agent 在别的身体上改名。§5.2 补上 Windows 上的执行安全写法。v12 仓库无需迁移即符合 v13。
- **v12**：§5.1 第 3 条补两点。其一，身体接入时没克隆成（例如网络拦了 SSH）、先在本地建了仓库，之后连上远端时**不得**把本地那段独立的历史推上去：合并后只保留远端一个父提交，内容照常并入。其二，已经混进来的陌生历史，如果那段历史里每个提交的顶层条目都在 §2 之内（同一个 agent 的身体接入时留下的），实现**可以**接受并记下它的根；含有 §2 以外内容的（例如代码仓库）照旧停止同步。起因（2026-10-06）：一部手机接入时开着拦 SSH 的 VPN，在本地建了仓库，联网后把这段历史并进了远端，其他身体都因此停了同步。v11 仓库无需迁移即符合 v12。
- **v11**：取消 §5.2 第 4 条「密钥不进提交」，§6 恢复为没有例外的「内容不做检查」：这条检查把身体名、agent id 这类并不保密的值也当成密钥，整天挡住记忆同步（2026-10-06）。灵魂仓库是私有的，保护靠 §7 的访问控制。v10 仓库无需迁移即符合 v11。
- **v10**：新增 §5.2「git 的执行安全」：灵魂目录可能被 agent 动过，实现执行 git 时**必须**不执行钩子、不用 fsmonitor、不读系统与全局配置、不跟 `file://` / `ext::` 协议，推送与拉取**必须**直接使用配置里的地址（不经 `origin`，`url.*.insteadOf` / `pushInsteadOf` 不生效），操作前删掉 `.git/config` 白名单以外的键；**不得**提交、检出（为链接）或合并符号链接；提交前**必须**检查暂存的改动里有没有这具身体自己的密钥，有就拒绝提交并提醒 agent。§6 相应写明这唯一的例外。§7 私钥路径必须是绝对路径并按 shell 规则加引号。v9 仓库无需迁移即符合 v10（含符号链接的仓库需要先把链接换成普通文件）。
- **v9**：§1 灵魂仓库必须由部署者自己创建、只属于一个 agent，与任何代码仓库（包括 Quetzal 源代码仓库）无关；§5 新增「只推到配置的地址」「拒绝不是灵魂仓库的远端」「拒绝外来历史」「agent 不得直接操作灵魂仓库的 git」「限制 git 的仓库搜索范围」五条实现要求；§3.4 README 模板写明这些。起因见 §5.1。v8 仓库无需迁移即符合 v9。
- **v8**：§3.3 冲突副本：两边都改过的文本文件，实现**可以**先采用较新的一版，把落选的一版另存为同目录的 `<名>.incoming.md`（被 `.gitignore` 忽略，不入库、不同步），交给 agent 裁决；§3.10 身体登记新增可选的 `meshKey`（网状层的节点公钥），`lastSeen` 改为「内容变化或超过 1 小时时更新」，不必每次推送都改；§5 提交可以细到每次改动一个，提交信息说明改了什么。v7 仓库无需迁移即符合 v8。
- **v7**：§7 认证：默认仍是每具身体一把部署密钥，新增部署者显式选择的两种方式——指定私钥、系统 ssh 配置（`~/.ssh/config` + ssh-agent）；远端地址允许 ssh 配置里的 Host 别名。v6 仓库无需迁移即符合 v7。
- **v6**：运行基座更名为 Quetzal，§3.12 技能文档 `metadata` 里的键改为 `quetzal-tool` 与 `quetzal-requires`（原 `windler-tool` / `windler-requires`）；实现只写新键名，读取时不依赖这两个键。v5 仓库无需迁移即符合 v6。
- **v5**：§2 新增可选目录 `skills/`（§3.12）：agent 沉淀的技能文档，采用 [Agent Skills](https://agentskills.io/specification) 开放标准的 `SKILL.md`，Hermes Agent 与 OpenClaw 可直接读取；只放意图说明，不放实现代码。v4 仓库无需迁移即符合 v5。
- **v4**：§6 取消全部内容检查；§1 允许顶层出现规范外的条目。灵魂仓库按设计只能是私有仓库（§7 只允许部署私钥访问），记忆里出现 IP、电话、密钥都是她自己的事，实现**不得**因内容拒绝提交；此前的检查曾两次把她的记忆挡在本地数天（版本号被当成 IP）。v3 仓库无需迁移即符合 v4。
- v3：§6 明确 IP 地址只指能定位设备或个人的地址：版本号、回环与保留段、公共 DNS 服务器不算；检查结果带行号。v2 仓库无需迁移即符合 v3。
- v2：常驻记忆取消字符上限，由实现在放进上下文时按预算展开；笔记改为最多 4 层的目录树，可以写一句话摘要。v1 仓库无需迁移即符合 v2，实现接入时把 `.soul-spec.json` 更新为 v2。
- v1：初版。

## 1. 仓库

- **一个 agent 对应一个仓库**，仓库**必须**是私有的，由部署者自己创建（例如在 GitHub 上新建 `<agent>.soul`），只存放这个 agent 的灵魂（v9）。
- 灵魂仓库**不得**与任何代码仓库共用，包括 Quetzal 自己的源代码仓库；**不得**把程序代码放进灵魂仓库，也**不得**把灵魂仓库的内容推到别的仓库（v9）。
- 命名**应当**为 `<agent 短名>.soul`，例如 `kaoru.soul`。
- 默认分支为 `main`，只使用这一个分支。
- 历史只追加：**不得**强制推送（force push），**不得**改写历史。撤销一律用反向提交。

## 2. 目录树（固定）

```
<agent>.soul/
├── .soul-spec.json            固定  规范版本
├── .gitattributes             固定  换行与文本属性
├── .gitignore                 固定  忽略临时文件
├── README.md                  固定  说明这是什么仓库（自动生成，不写任何个人内容）
├── agent.json                 必需  身份
├── SOUL.md                    必需  人格
├── memories/                  必需
│   ├── MEMORY.md              必需  agent 自己的常驻笔记
│   └── USER.md                必需  关于用户的认识
├── journal/                   必需  情节记忆（含 .gitkeep）
│   └── <body>/
│       └── <YYYY-MM-DD>[-<slug>].md
├── notes/                     必需  共享的长期笔记（含 .gitkeep），目录树
│   └── [<分类>/…/]<主题>.md     最多 4 层
├── bodies/                    必需  身体登记（含 .gitkeep）
│   └── <body>.json
├── skills/                    可选  技能文档（Agent Skills 规范），每个技能一个目录
│   └── <skill-name>/
│       └── SKILL.md
└── locks/                     可选  协调锁（按需创建）
    └── consolidation.json
```

- 顶层**可以**出现其他条目（例如 agent 自己放的脚本目录）：这是她的仓库。实现**不得**删除它们，也不必报告。
- 标「固定」与「必需」的条目缺失时，实现**必须**在接入时自动补齐（见 §4）。
- 所有文本文件使用 UTF-8 编码、LF 换行。单个文件**不得**超过 1 MiB。**不得**提交二进制文件。

## 3. 文件格式

### 3.1 `.soul-spec.json`（固定内容）

```json
{ "spec": "soul-repo", "version": 14 }
```

### 3.2 `.gitattributes`（固定内容）

```
* text=auto eol=lf
*.md text diff=markdown
*.json text
```

### 3.3 `.gitignore`（固定内容）

```
*.tmp
*.swp
.DS_Store
*.incoming*.md
```

`*.incoming*.md` 是冲突副本（v8）：合并时两边都改过同一个文本文件（`SOUL.md`、笔记、技能文档等），实现**可以**先采用提交时间较新的一版，让仓库继续同步，同时把落选的一版写到同目录的 `<名>.incoming.md`，交给 agent 裁决。副本只在这具身体上、不入库；agent 看过后保留现在的一版就删掉副本，想要另一版或合并两者，就改好原文件再删掉副本。读取笔记、生成索引、映射到其他框架时，实现**必须**跳过副本。

### 3.4 `README.md`（固定内容）

说明这是一个灵魂仓库、指向本规范，并提醒保持私有、不要手动修改。内容由实现按模板生成（模板见 `soul-repo.ts` 的 `README_TEMPLATE`）。不写入任何个人信息。

### 3.5 `agent.json`（身份）

```json
{
  "id": "0b6d2c1e-6c1f-4a53-9a57-2f1f0f3c9d10",
  "name": "kaoru",
  "displayName": "显示名",
  "pronouns": "",
  "description": "",
  "color": "#F0A35E",
  "language": "zh-CN",
  "createdAt": "2026-09-28T02:00:00.000Z"
}
```

| 字段 | 规则 |
|---|---|
| `id` | UUID v4，诞生时生成，**永不改变**；实现用它拒绝合并属于另一个 agent 的仓库 |
| `name` | `^[a-z0-9][a-z0-9-]{0,39}$` |
| `displayName` | 非空，界面与称呼使用 |
| `color` | `#RRGGBB` |
| `language` | BCP 47 语言标签 |
| `seed` | 可选。`true` 表示自动生成、尚未被修改过的种子身份。种子身份遇到远端身份时让位 |

合并规则：字段级合并，本地优先，`id` 除外。

### 3.6 `SOUL.md`（人格）

自由 Markdown，作为系统提示的第一段。第一行应当是 `# <显示名>`。

合并规则：采用提交时间较新的一方；本地为空或仍是种子人格时采用对方。落选版本保留在历史中；两边都改过时，落选版本可以另存为冲突副本交给 agent 裁决（§3.3）。

### 3.7 `memories/MEMORY.md`、`memories/USER.md`（常驻记忆）

- 由若干条目组成，条目之间用 `\n§\n` 分隔，文件以 `\n` 结尾，空文件表示没有条目。
- 条目是去掉首尾空白后的非空文本，可以多行，但**不得**包含单独成行的 `§`。
- **没有字符上限**。仓库里的常驻记忆可以任意增长。
- 实现放进上下文时**应当**有预算：放得下就全部展开；放不下时优先展开与当前话题相关的条目，其余按新近程度补足，并告诉 agent 还有多少条没有展开、可以检索。
- 写回自身有上限的框架（例如 Hermes Agent 的 `memory_char_limit`）时，按该框架的上限截取，截取**不得**写回仓库。
- 语义与 Hermes Agent 的 `memory` 工具一致：add / replace / remove。

合并规则：条目级三方合并，双方新增都保留，任一方删除即删除。

### 3.8 `journal/<body>/<YYYY-MM-DD>[-<slug>].md`（日记）

- **每具身体只写自己的目录**，因此天然没有冲突。
- 格式：第一行 `# <YYYY-MM-DD> · <body>`；每段经历为 `## <HH:MM> <标题>` 加正文，只追加。
- 从框架导入的日记（例如 OpenClaw 的 `memory/YYYY-MM-DD*.md`）保持原文件名与内容。

### 3.9 `notes/[<分类>/…/]<主题>.md`（共享笔记，目录树）

- 笔记按目录树组织，路径写作「分类/子分类/主题」，**最多 4 层**，第 4 层必须是文件。例如 `notes/身体/honor9/硬件.md`。
- 路径的每一段（目录名与文件名）由原文得到：去掉 `\ / : * ? " < > |`、控制字符与空白（替换为 `-`），去掉开头的 `.`，最长 60 个字符；再去掉结尾的 `.`，Windows 保留名后面加 `_`（v13，见 §3.13）。超出层数时，多余的段并入最后一段（用 `-` 连接）。
- 第一行 `# <主题>`。其后**可以**有一行以 `> ` 开头的一句话摘要，实现用它生成记忆目录（索引）。其余为自由 Markdown。
- 目录里只放笔记与子目录；空目录不保留（`notes/` 自身为空时放 `.gitkeep`）。**不得**提交自动生成的索引文件，索引由实现在读取时即时生成。
- 合并规则：采用提交时间较新的一方，落选版本保留在历史中；两边都改过时，落选版本可以另存为冲突副本交给 agent 裁决（§3.3）。

### 3.10 `bodies/<body>.json`（身体登记）

```json
{ "body": "honor9", "kind": "runtime", "runtime": "1.0.0", "meshKey": "<43 个字符的 base64url>", "uuid": "<8-4-4-4-12 的小写十六进制>", "lastSeen": "2026-09-28T02:00:00.000Z" }
{ "body": "hermes-pc", "kind": "bridge", "framework": "hermes", "bridge": "0.2.0", "host": "pc", "lastSeen": "…" }
```

- `body` 与文件名相同，只能用 `[a-z0-9-]`，**不得**是 Windows 的保留名（v13，§3.13）。每具身体只写自己的文件。`lastSeen` 在登记内容变化、或距上次更新超过 1 小时时更新（v8；不必每次推送都改，免得历史里塞满无意义的提交）。
- `meshKey`（v8，可选）：这具身体在网状层（多具身体实时连成一个心智）里的节点公钥，ed25519 原始公钥的 base64url（43 个字符）。其他身体建立连接时**必须**用这里登记的公钥核对对方，不得信任同步服务转告的公钥（灵魂仓库是信任根）。公钥不能定位设备，不违反下一条。
- `uuid`（v14，可选，只有运行基座写）：这具身体的 uuid，RFC 9562 格式的小写字符串（`8-4-4-4-12`）。运行基座由设备自身的标识（Linux 的 machine-id、Windows 的 MachineGuid、安卓的 ANDROID_ID 等）派生：`sha256("quetzal-body-uuid/1\n" + 原始标识)` 取前 16 字节，设 version 8 与 variant 位；取不到设备标识时为随机的 version 4。**不得**写入原始的设备标识（它能定位设备，违反下一条）。uuid 不是密码学身份：其他身体解析 uuid 时**必须**以这里的登记为准找到身体名，再经已经认证过的连接找那具身体，并核对它自报的 uuid 与登记一致，不一致就拒绝；同一个 uuid 出现在多具身体的登记里时**必须**拒绝解析并说明，**不得**替用户自动改（通常是同一台设备上装了两份运行基座：只留一份，或在其中一具身体上换一个随机 uuid）。格式不对的 `uuid` 当作没有。
- **不得**写入 IP 地址、MAC 地址、序列号等可以定位设备或个人的标识。

### 3.12 `skills/<skill-name>/SKILL.md`（技能文档）

agent 把做过多次、步骤稳定的流程沉淀为技能：**只同步意图**（用途、参数、实现思路、依赖、验证方法、坑），**不同步实现代码**——每具身体按文档在本地自己实现（运行基座：`QUETZAL_HOME/tools/<名>/`；Hermes / OpenClaw：各自的 skills 目录）。格式遵循 Agent Skills 开放标准：

```markdown
---
name: web-search
description: 搜索网页并返回标题、链接与摘要。查资料、核实事实时用。
compatibility: 需要命令 curl
metadata:
  quetzal-tool: web_search
  quetzal-requires: curl
---

## 用途
……
```

- 目录名与 `name` 相同：`^[a-z0-9]+(-[a-z0-9]+)*$`，最长 64 字符（运行基座把工具名里的 `_` 换成 `-` 得到它），**不得**是 Windows 的保留名（v13，§3.13）。
- `name`、`description` 必需；`compatibility`、`license`、`metadata`（字符串映射）可选。运行基座写入 `metadata.quetzal-tool`（对应的工具名）与 `metadata.quetzal-requires`（依赖的命令，逗号分隔），其他实现可以忽略。
- 正文自由 Markdown；可以有 `references/` 等子目录（规范建议），但**不得**放可执行实现（实现是身体的，不是灵魂的）。
- 合并规则：采用提交时间较新的一方，落选版本保留在历史中；两边都改过时，落选版本可以另存为冲突副本交给 agent 裁决（§3.3）。

### 3.11 `locks/consolidation.json`（整理租约）

```json
{ "body": "honor9", "until": 1790530000000 }
```

- 表示某具身体正在整理常驻记忆，`until` 为毫秒时间戳，有效期 30 分钟。
- 取得方式：写入租约后推送成功，即为取得（比较并交换）。释放时删除该文件。

### 3.13 路径在每一种身体上都放得下（v13）

同一个灵魂会被检出到 Linux、安卓与 Windows 上。Windows 的文件系统最严，所以：

- 仓库里每个路径的每一段**应当**满足：不是 Windows 的保留名（`CON`、`PRN`、`AUX`、`NUL`、`COM0`–`COM9`、`LPT0`–`LPT9`、`COM¹²³`、`LPT¹²³`、`CONIN$`、`CONOUT$`，不分大小写，带扩展名也算，例如 `con.md`）；不以 `.` 或空格结尾；不含 `< > : " \ | ? *` 与控制字符；不是 `.git` 在 NTFS 上的别名（`git~1`、`.git.` 等）。
- 仓库里**不应当**出现只差大小写的两个路径（包括目录，例如 `Notes/a.md` 与 `notes/b.md`）。
- 实现写入时**必须**规避（笔记路径段、身体名、技能名，见 §3.9、§3.10、§3.12）。
- 别的实现或旧版本已经写进去的放不下的路径：Windows 上的实现**必须**照常克隆、拉取、合并与推送（不得因此停止同步），只是不把这些路径写进工作区（例如 git 的 sparse-checkout），提交与推送时在仓库里原样保留；并**应当**提醒 agent，由她在别的身体上改名。

## 4. 接入与补齐

实现接入仓库时（克隆或本地初始化之后）**必须**补齐 §2 中缺失的固定与必需条目：
- 固定文件按 §3 的固定内容写入；
- `agent.json` 缺失时生成种子身份；
- `SOUL.md` 缺失时按身份生成种子人格；
- 空目录放入 `.gitkeep`。

补齐产生的变更作为一次提交：`补齐灵魂仓库规范结构（<body>）`。

## 5. 提交约定

- 作者：`<displayName> (<body>)`，邮箱 `<name>@<body>.local`。
- 提交信息：`<说明>（<body>）`。例如 `做梦：……（honor9）`、`note_save：笔记 身体/honor9/硬件（honor9）`、`同步 Hermes Agent 的变更（hermes-pc）`、`撤销 1a2b3c4（honor9）`。
- 提交的粒度由实现决定，可以细到每次改动一个提交（v8：运行基座在 agent 的每次工具调用之后，只要灵魂目录有变化就提交一次）。
- 每次推送前拉取合并，推送被拒时重新拉取合并后再推送；**不得**强制推送。

### 5.1 只同步灵魂仓库自己的历史（v9）

实现**必须**：

1. **只推到配置的地址**：每次推送前把本地克隆的 `origin` 校正为配置里的灵魂仓库地址，不使用克隆里被手动改过的远端。
2. **拒绝不是灵魂仓库的远端**：远端没有 `agent.json`，却有 §2 以外的顶层内容时（例如一个代码仓库），拒绝合并。只有 README、LICENSE、`.gitignore` 等的新建仓库可以接入。
3. **拒绝外来历史**：每个克隆记录灵魂仓库已知的根提交（第一次同步时记录，存在克隆的 `.git` 里，不入库）；之后本地或远端出现陌生的根提交，说明别的仓库的历史混了进来，**必须**停止同步（不合并、不推送）并提醒，交给人处理。例外（v12）：只经过陌生根提交、不经过已知根提交的那些提交，顶层条目全都在 §2 之内时，那是同一个 agent 的身体接入时在本地建立的历史，实现**可以**接受并记下它的根。反过来，接入时在本地建了仓库的身体，连上远端时**不得**把本地那段独立的历史推上去：合并后换成只有远端一个父提交的普通提交，内容不变。
4. **agent 不得直接操作灵魂仓库的 git**：实现应当在 agent 的命令执行工具里拦下针对灵魂目录的 git 命令，并在 agent 的指引里写明。
5. 执行 git 时**应当**限制仓库搜索范围（例如 `GIT_CEILING_DIRECTORIES`），灵魂目录的 `.git` 丢失时不得退到上层目录里的别的仓库。

### 5.2 git 的执行安全（v10）

灵魂目录在 agent 所在的机器上，agent 的命令可能碰到它（即使实现在命令执行工具里拦截，换个写法也拦不住）。所以实现**必须**把灵魂目录里的一切当作不可信输入：

1. **不执行仓库里的代码**：每次执行 git 都关掉钩子与 fsmonitor（`-c core.hooksPath=/dev/null -c core.fsmonitor=false`），不读系统与全局配置（`GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=/dev/null`），不允许 `file://` 与 `ext::` 协议（测试除外）。查看差异时不用外部 diff 与 textconv。
2. **地址只来自实现的配置**：推送用 `git push <配置的地址> HEAD:refs/heads/<分支>`，拉取用 `git fetch <配置的地址> +refs/heads/<分支>:refs/remotes/origin/<分支>`，不经 `origin`；每次提交、拉取、推送前删掉 `.git/config` 里白名单以外的键（白名单：`core` 的基本键、`user.name/email`、`remote.origin.url/fetch`、`branch.<分支>.remote/merge`、`extensions.*`），`url.*.insteadOf`、`core.sshCommand`、`filter.*`、`include.*` 等一律不保留。
3. **不收符号链接**：检出时 `core.symlinks=false`；暂存区里的符号链接（mode 120000）不提交；远端的分支里有符号链接时拒绝合并并提醒，交给人处理。
4. ~~密钥不进提交~~（v11 取消）。原文：提交前取这具身体自己的密钥值（实现的令牌、主密钥、部署与节点私钥、同步服务令牌、模型 Key、保密库里的值，12 个字符以上），暂存的改动（新增的行）里出现任何一个就拒绝整个提交、清空暂存区，并以同步提醒告诉 agent 是哪些文件；文件改好之前灵魂目录的改动不同步。合并提交（内容来自远端，本地改动已在合并前单独提交并检查）不检查。本地有因此没提交的改动时先不合并远端。
5. 实现**应当**让 agent 的命令在沙箱里运行，灵魂目录的 `.git` 对 agent 只读（运行基座：`runtime/src/sandbox.ts`）。
6. **Windows（v13）**：`/dev/null` 在 Windows 上会被解析成「当前盘根目录下的 `dev\null`」，普通用户能在那里建目录、放钩子，所以钩子目录与全局配置**必须**指向实现自己的、agent 不可写的空目录与空文件；**必须**打开长路径（`core.longpaths=true`，系统配置不读，它不会自己生效）。为了让 §3.13 放不下的路径能进索引、照常合并，实现**可以**关掉 `core.protectNTFS`，但这时**必须**自己把 `.git` 的 NTFS 别名、带冒号的流名与保留名一并排除在工作区之外（运行基座用 sparse-checkout）。

起因（2026-10-05）：一具身体上的 agent 推送失败后，自己用 shell 把灵魂目录的 `origin` 改成了运行它的程序的公开源代码仓库并 `reset` 过去，实现随后按常规推送，一个灵魂提交进了公开仓库；改回地址后，实现又把源代码的历史合并进了灵魂仓库。上面五条分别堵住这条链上的每一环。

## 6. 内容：不做检查

灵魂仓库是 agent 自己的私有仓库，里面是她的人格与记忆。实现**不得**对内容做任何脱敏、隐私或敏感信息检查，**不得**因内容拒绝提交：她写什么就提交什么。没有例外（v11 取消了 v10 对这具身体自己的密钥的检查）。保护靠 §7 的访问控制（私有仓库 + 每具身体专属的部署私钥），不靠审查内容。

实现**可以**对会拖慢 git 的东西（二进制文件、超过 1 MiB 的文件）记一条提醒，但仍然提交。

实现侧的配置（API Key、网关令牌、飞书凭据、部署私钥）保存在实现自己的密钥目录中，与灵魂仓库分离——这是为了换身体时不必跟着走，不是因为不能放。

## 7. 认证：必须用 SSH；默认每具身体一把部署密钥，部署者可改用自己的钥匙（v7）

- 远端地址**必须**是 SSH 形式：`git@<host>:<owner>/<repo>.git` 或 `ssh://git@<host>/<owner>/<repo>.git`；`~/.ssh/config` 里的 Host 别名（如 `git@github-personal:owner/repo.git`）也可以。**不得**使用 HTTPS、个人访问令牌或密码。
- 私钥路径（部署私钥或部署者指定的私钥）**必须**是绝对路径、不含控制字符，放进 `GIT_SSH_COMMAND` 时**必须**按 shell 规则加引号（v10）。
- **默认：每具身体一把专属密钥**：ed25519，在本机生成。私钥只存放在本机、权限 `0600`（运行基座为 `QUETZAL_HOME/secrets/soul_ed25519`，灵魂桥为 `~/.agent-soul/<agent>/id_ed25519`），**不得**提交到任何仓库，**不得**在身体之间复制。公钥以 **Deploy key（勾选 Allow write access）** 的形式添加到该灵魂仓库，每把密钥只能访问这一个仓库，吊销只需删掉它。实现访问远端时只使用这把私钥：`ssh -i <私钥> -o IdentitiesOnly=yes`，不回退到 ssh-agent 或默认密钥；私钥不存在时拒绝访问远端并明确提示，不静默回退。
- **部署者可以改用自己的钥匙**（v7 起，由部署者在实现的配置里显式选择，默认不生效）：（a）**指定私钥**：仍是 `ssh -i <该私钥> -o IdentitiesOnly=yes`，只用它；（b）**系统 ssh 配置**：不传 `-i`，钥匙由该机器的 `~/.ssh/config`（IdentityFile）与 ssh-agent 决定。这两种方式把访问范围交给了部署者自己的钥匙，实现**必须**在界面上说明这一点，且仍然不得把任何私钥写进灵魂仓库。
- **吊销**某具身体：在仓库 Settings → Deploy keys 删除它的公钥。
- 例外：只在自动化测试中，可以通过环境变量 `SOUL_ALLOW_LOCAL_REMOTE=1` 使用本地路径作为远端。
